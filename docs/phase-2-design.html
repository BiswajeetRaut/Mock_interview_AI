01

Decisions

Seven decisions, made jointly, with the alternatives we rejected and why. These are the load-bearing choices — everything in the roadmap follows from them.

D-01 Disable the coding runner immediately; rebuild it sandboxed in 2B
Context

/coding/run executes attacker-controlled code as the app user with no isolation and no auth. It can read GROQ_API_KEY and the Firebase admin credential.

Decision

Feature-flag the endpoint off in week 1. Rebuild in 2B as a separate execution service on a dedicated node pool: gVisor runtime class, non-root, read-only rootfs, no network, no mounted secrets, hard cgroup CPU/memory limits, 5-second deadline.

Rejected
  • Harden in place — cannot be made safe inside the API process. Any escape lands next to the secrets.
  • Drop code execution entirely — real test-case feedback is genuine product value; we're deferring it, not abandoning it.
D-02 Event-driven orchestrator with worker agents, replacing the session engine
Context

Capacity is currently coupled to user count through a 40-thread pool. Adding replicas moves the cliff without removing it.

Decision

API accepts an answer, appends an event, and returns. An orchestrator consumes the stream and dispatches work to stateless agent workers. Results flow back as events and are pushed to the client over SSE. Worker pool size is governed by LLM quota, not by user count.

services/session_engine.py is deleted. The supervisor, evaluator, and three question agents survive unchanged — they are already stateless and become the workers. LangGraph remains as the orchestrator's state machine with a Postgres checkpointer.

Consequences
  • Burst becomes queue depth — an observable, alertable number — instead of a thread-pool cliff.
  • Partitioning the stream by session_id gives ordered per-session processing, which eliminates the non-atomic session lock defect rather than fixing it.
  • Two code paths exist during the 2A→2B cutover. Accepted, and time-boxed.
D-03 Postgres for state, Redis for hot path and (in 2B) the broker
Decision

Postgres holds LangGraph checkpoints (AsyncPostgresSaver), sessions, turns, durable results, the outbox, and the 2B question bank. Redis holds rate-limit counters, the hot session read cache, and — from 2B — Streams as the broker, with consumer groups giving ordered per-session partitions.

Rejected
  • Kafka — correct at Phase 3 scale, but real operational weight for two people. Redis Streams is a clean migration source when we outgrow it.
  • Temporal — honestly the right abstraction; a LangGraph interrupt is a poor man's durable signal. Too large a dependency and rewrite for this window. Explicitly on the Phase 3 table.
  • NATS JetStream — reasonable middle path, but a third system to learn for a benefit we can't yet measure.
Hosting, decided 19 Aug 2026

K8s: GKE Autopilot. Google manages node provisioning and patching — the right tradeoff for a 2-person team — and Autopilot has strong support for the custom-metric HPA the capacity plan already calls for (interview_turns_inflight, not CPU).

Postgres: Neon. The direct analog to MongoDB Atlas — one connection string, autoscaling compute, a built-in pooler (removes the PgBouncer story from the backlog entirely — see the §6 callout below), and database branching, which gives CI an ephemeral DB per test run instead of a shared fixture. pgvector is supported, which D-08 depends on. Neon is cloud-agnostic, so this choice doesn't lock in the GKE decision either way.

One caveat worth carrying forward: Neon sits outside GCP's VPC, so GKE↔Neon traffic crosses the public internet, TLS-encrypted. That's fine at Phase 2A scale. If the Epic 6 load test shows it as a measured latency contributor, the fix is a provider swap to Neon's VPC-peering tier or a hyperscaler-managed DB — not a redesign, since the schema and access pattern don't change.

Redis: GCP Memorystore — decided 19 Aug 2026, and here the reasoning differs from Postgres's. Redis is hit on every rate-limited request (P2-106), not once per turn, and in 2B it becomes the Streams broker — the actual message bus the orchestrator depends on. That hit-rate makes the public-internet hop we accepted for Neon a worse tradeoff here, so Memorystore's same-VPC placement (no public hop, no egress cost, lowest latency) is the natural fit given GKE Autopilot is already the target. Rejected Redis Cloud for the same reason Neon's caveat exists — cloud-agnostic and easy to spin up, but adds latency on a path that's now hot rather than occasional. Rejected self-hosting in-cluster for the same reason CloudNativePG was rejected: real ops burden (persistence, failover) that a 2-person team shouldn't take on when a managed option fits this cleanly.

D-04 Hybrid question bank: pre-generate offline, personalize at runtime
Context

The three-step reason → generate → critique chain is 3 of the 5–6 calls per turn. It is the cost driver, the latency driver, and the quota driver simultaneously.

Decision

An offline pipeline generates and vets question packs into a Postgres bank, indexed by agent type, round type, difficulty, and topic tags. At runtime the LLM only selects, personalizes, and evaluates. Bank hits return in milliseconds.

Staged: W5 of 2A collapses the live chain from 5–6 calls to 2–3 by merging steps into single structured calls — roughly 70% of the win, available six weeks earlier. 2B adds the bank itself.

Consequences

Bank questions are vetted once and reused, so per-question quality goes up; per-candidate novelty goes down. Personalization and topic-coverage tracking are what preserve the bespoke feel. This is a product tradeoff and needs a quality gate before rollout — see §7.

D-05 Write the event log in week 2, six weeks before anything consumes it
Decision

When state moves to Postgres in W2, every turn transition also writes a domain event to an outbox_events table in the same transaction. Nothing reads it until W7.

Rationale

The seam is nearly free to build while we're already rewriting the persistence layer, and expensive to retrofit later. It makes 2B a cutover rather than a rewrite, and it gives us six weeks of real production event data to validate the orchestrator design against before we commit to it.

D-06 Foundation before architecture — and this is a correctness argument, not a capacity one
Context

The repo has zero tests, zero metrics, no container, and no CI.

Decision

Weeks 1–4 deliver security, externalized state, the deployment pipeline, and observability. The orchestrator rewrite starts in week 7.

Rationale

Starting the distributed refactor first means performing it blind — no way to detect a regression and no way to see it in production. That is the specific failure mode that turns a six-week plan into a sixteen-week one. The sequencing is about being able to verify the interesting work, not about deferring it.

D-07 Multi-provider LLM routing from week 5 — one API key cannot reach the target
Context

Even after cutting to 2.5 calls per turn, 10,000 concurrent interviews needs roughly 17,000–25,000 requests per minute. No single account grants that.

Decision

Introduce a provider abstraction in W5: key-pool rotation, per-provider token buckets, health-based failover across Groq / Cerebras / Together / Fireworks, and a circuit breaker per provider. Model choice becomes config, not an import.

Consequences

This is the component that makes the Phase 2 target reachable at all, and it is also the natural insertion point for owned inference in Phase 3. Worth building carefully.

D-08 Three-tier agent memory — and vectors only where a WHERE clause won't do
Context

Today the supervisor's entire memory is coverage_context and a scratchpad, both scoped to a single session and both discarded when it ends. A candidate's fifth interview knows nothing about their first four — which undercuts the core product promise, longitudinal improvement. Separately, the supervisor prompt grows with turn count, so per-turn token cost is O(turns).

Decision

Working memory in Redis (compacted live context), long-term memory in Postgres (structured candidate profile, asked-question ledger), episodic memory as pgvector embeddings over completed-session summaries. Retrieval is policy-driven, not naive top-k. Full design in §4.

The discipline that keeps this cheap

Most of what we want from "memory" is relational, not semantic. Has this candidate been asked about LRU caches before? is an indexed lookup, not a similarity search. What are their persistent weak topics? is a GROUP BY over evaluations. Vectors earn their place for exactly two jobs — narrative recall across sessions, and finding comparable candidates for difficulty calibration. Everything else stays in SQL, where it is faster, cheaper, exact, and debuggable.

Store

pgvector, not a dedicated vector database. One embedding per completed session means ~300K vectors at a lakh of users — comfortably within pgvector's range. Pinecone or Qdrant would add an operational system for two people in exchange for headroom we won't touch until Phase 3.

Staging

Schema and writes land in W2 (same argument as D-05 — nearly free while we're already building the persistence layer, expensive to retrofit, and it starts accumulating real data immediately). Working-memory compaction lands in W5, where it serves the cost workstream directly. Retrieval and episodic vectors are 2B.

Why HPA on CPU would be wrong

These pods are I/O-bound proxies waiting on an LLM. CPU sits near idle while the pod is completely saturated on in-flight turns, so a CPU-target HPA will refuse to scale during the exact incident you built it for. We scale on a custom Prometheus metric — interview_turns_inflight, target ~20 per pod — with CPU kept only as a secondary safety trigger.

-- plus checkpoints / checkpoint_writes, managed by AsyncPostgresSaver
Two details doing quiet work

UNIQUE (session_id, idx) makes turn writes idempotent, so a redelivered event replays harmlessly — the property that lets us use at-least-once delivery without deduplication logic. And locked_until as a lease rather than a boolean means a worker that dies mid-turn releases its session automatically instead of wedging it forever.

Agent memory

Three tiers with different lifetimes, different stores, and different jobs. The organising rule is that each tier answers a question the tier below it cannot answer cheaply.

Tier 1 — Working memory (Redis, session-scoped)

The compacted context the supervisor actually needs on every call. Not a naive cache of the Postgres row — a purpose-built working set, pre-assembled so we don't re-serialize a growing session object 12 times per interview.

The important change here is rolling summarization. Today _build_turn_history() pastes the last ten turns verbatim into the prompt, so token cost grows with turn count. Instead we keep a running natural-language summary plus the last two or three turns in full, and refresh the summary every few turns.

// current: verbatim history
supervisor prompt at turn 10 ≈ 2,400 tokens O(turns)
// with rolling summary + last 3 verbatim
supervisor prompt at turn 10 ≈ 1,100 tokens O(1)

≈ 45% fewer input tokens on the hot path, flat in interview length
Why this lands in W5, not later

Compaction is not really a memory feature — it is a cost feature that happens to need a memory structure. It reduces supervisor input tokens on every single turn, which is precisely the W5 chain-reduction goal. Building it alongside the call merge means one prompt-engineering effort and one quality gate instead of two.

Tier 2 — Long-term memory (Postgres, candidate-scoped)

Structured, queryable, exact. This is what actually designs the next interview, and it is deliberately relational — no embeddings involved.

candidate_profiles (user_id PK FK→users,
                    proficiency JSONB,      -- {"concurrency": {"score": 42, "n": 7, "trend": "up"}, …}
                    persistent_weak_topics TEXT[],
                    persistent_strong_topics TEXT[],
                    calibrated_difficulty TEXT,
                    sessions_completed INT,
                    avg_think_time_seconds INT,     -- also feeds the §6 capacity model
                    updated_at)

asked_questions    (id PK, user_id FK, session_id FK,
                    question_hash TEXT,     -- normalized text hash, exact dedup
                    topic_tag TEXT, agent_type TEXT,
                    difficulty TEXT, score_pct INT, asked_at)
                    INDEX (user_id, topic_tag), INDEX (user_id, question_hash)

Two things this fixes that are live product bugs today:

  • Cross-session repetition. already_asked_topics is session-scoped, so a candidate running five interviews can be handed the same question five times. An indexed lookup on (user_id, question_hash) ends that — and it costs one query, not a similarity search.
  • Difficulty restarts from scratch every session. Every interview begins at whatever the user picked, ignoring that we already know how they perform. calibrated_difficulty seeds the graph's opening state instead.

Tier 3 — Episodic memory (pgvector, narrative)

One embedding per completed session, over an LLM-written summary of how the interview actually went — not the scores, which we already have relationally, but the texture. "Reached a working solution but only after two hints; explains tradeoffs well; visibly uncomfortable when pushed on scale."

Two jobs, and only two:

  1. Narrative recall — when a returning candidate starts a session, retrieve their two or three most relevant prior summaries so the supervisor opens with real continuity rather than a cold start.
  2. Difficulty calibration by analogy — find comparable candidates at a similar stage and use what worked for them to pick an opening difficulty and topic mix.
session_summaries (session_id PK FK, user_id FK,
                   summary TEXT,              -- LLM-written, ~150 words
                   embedding VECTOR(768),     -- pgvector
                   role TEXT, company TEXT, overall_score INT,
                   created_at)
                   INDEX USING hnsw (embedding vector_cosine_ops)
                   INDEX (user_id, created_at DESC)

Retrieval policy — rules first, similarity last

The retrieval is heuristic by design. Naive top-k over everything would be slower, more expensive, and less predictable than a rule that already knows what it needs.

WhenTierWhat is fetchedCost
Session startLong-termProfile row — always. Seeds difficulty and the topic plan.1 query
Session start, if ≥2 priorsEpisodicTop-3 summaries by 0.5·similarity + 0.3·recency + 0.2·role_match1 ANN query
Every question generationLong-termAsked-question hashes and topic tags for this user1 indexed query
Every supervisor turnWorkingRolling summary + last 3 turns + coverage1 Redis GET
Session endAllWrite-back: summarize, embed, aggregate proficiencies1 LLM + 1 embed

Net effect on the hot path: zero additional LLM calls per turn. Retrieval is two queries at session start and one write-back at session end — it does not touch the per-turn budget the capacity model in §6 depends on.

This tier makes us a data controller

Long-term and episodic memory turn a stateless interview tool into a system holding durable behavioural profiles of named individuals, alongside their resumes. Under India's DPDP Act that carries retention limits and a genuine erasure obligation — and erasure has to cascade to derived data, meaning embeddings and aggregated proficiencies, not just the source rows. Add the retention columns and a cascading delete path in W2 while the schema is being written. It is a few hours then and a migration under legal pressure later.

Deliberately not in 2A

Event broker cutover, orchestrator/worker split, SSE frontend, question bank, sandboxed executor, and memory retrieval — episodic embeddings and the policy in §4. All are 2B, weeks 7–12.

The pattern in both deferrals is the same, and it is the main thing protecting this schedule: W2 writes the schema for things nothing reads until W7. The outbox and the memory tables both cost hours while the persistence layer is already open, and both would cost weeks to retrofit. By the time we build the consumers, they have five weeks of real production data to be built against rather than guessed at.

The assumption most likely to be wrong

90 seconds of think time per turn. If real candidates answer in 45 seconds, every number above doubles and 2A alone will not reach the target — the question bank moves from 2B into 2A. Instrumenting actual think time in week 4 is therefore a higher-priority metric than it looks, because it is the input that decides whether the week-6 load test can pass at all.

08

Sketch: Phase 3, toward 1M concurrent

Not designed yet — deliberately. It gets designed after the week-6 load test replaces our estimates with measurements. What we already know changes at that scale:

  • Inference goes in-house. At 83,000 calls/sec no commercial API tier exists. Self-hosted vLLM on GPU nodes with a fine-tuned small model for evaluation and routing; commercial APIs reserved for the hardest generation paths. The W5 LLM router is the seam this plugs into.
  • Redis Streams gives way to Kafka. Partition count, retention, and replay across regions stop being optional.
  • Postgres shards by session_id — Citus or an application-level split — with completed interviews aged into object storage.
  • Multi-region active-active, with interviews pinned to the region they started in. Interview sessions are short-lived, which makes this far easier than most stateful workloads.
  • Temporal becomes worth reconsidering (D-03). At Phase 3 saga complexity, hand-rolled orchestration stops paying for itself.

Next action: week 1 begins now. Security lockdown, per §5.
