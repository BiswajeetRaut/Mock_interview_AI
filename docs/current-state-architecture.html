01

What the system is

A single-page React app drives a voice-first mock interview. The candidate configures a session (company, role, rounds, topics, optional resume), then a FastAPI backend runs an agentic LangGraph loop that generates a question, waits for the answer, scores it, and reasons about what to ask next. Speech-to-text and text-to-speech both run in the browser — the Web Speech API and speak-tts — so no audio ever touches the server. That is a genuinely good architectural accident and worth preserving.

The whole thing is one Python process holding all state in module-level dicts, one Vite dev server, and one Groq API key. There is no container, no CI, no test, no migration, no metric, and no log aggregation. It is a well-structured prototype, not a deployable service — and it should be read that way.

The load-bearing detail

Both state stores are Python dicts inside the process, and the LangGraph checkpointer is MemorySaver(). The REDIS_URL path in session_engine.py only externalises the session summary dict — the actual graph checkpoint that Command(resume=…) needs is still RAM-only. So even with Redis configured, a session is pinned to the process that created it.

03

The turn — where time actually goes

One "turn" is the unit of work: candidate answers, server responds with the next question. Understanding this path is understanding the whole load model, because every LLM call in the chain happens inside the HTTP request, sequentially, while a thread is held.

Tail risk is severe

build_llm() in agents/shared.py sets timeout=8, max_retries=0. A turn chains up to six of these. If Groq is degraded, a single turn can hold its thread for 48 seconds before every stage silently falls through to a heuristic and returns a low-quality question. There is no circuit breaker, no bulkhead, and no signal to the client that quality was degraded — the user just gets a worse interview and never knows why.

Two behaviours worth calling out

  • A new ChatGroq client is constructed per call. build_llm() is invoked fresh at each of the ~48 sites. That means no connection pooling and repeated client setup on the hot path.
  • Exceptions are swallowed at nearly every layer. start_session catches graph failures into a discarded variable; submit_answer wraps invoke in except Exception: pass; each agent step falls back silently. The system is resilient in the sense that it never 500s — and unobservable in the sense that you cannot tell a healthy turn from a totally failed one.
04

Load model and saturation math

Three independent ceilings. The lowest one wins, and today they are very far apart — which tells us exactly what to fix first.

Ceiling A — the threadpool

Every route handler is declared def, not async def. FastAPI therefore runs each in Starlette's AnyIO worker threadpool, which defaults to 40 threads. A turn holds its thread for the entire LLM chain.

// per process, single uvicorn worker
threads = 40
turn_hold_time = 4 s (typical)
peak_turn_throughput = 40 / 4 = 10 turns/sec
// but a candidate is idle ~60s between turns, so:
duty_cycle = 4 / 64 ≈ 0.0625
concurrent_interviews ≈ 40 / 0.0625 ≈ 640

640 concurrent interviews looks survivable — until you notice it assumes perfectly smooth arrivals. Real traffic is bursty, and the moment 41 candidates submit within the same 4-second window, request 41 queues behind a thread rather than failing fast. There is no queue-depth metric to see it happen.

Ceiling B — memory, and it is unbounded

This is the one that actually kills the process. MemorySaver retains a full state snapshot per graph super-step, and nothing ever evicts it. SESSION_STORE and THREAD_STORE also grow forever — SESSION_TTL_SECONDS is only honoured on the Redis path.

state per turn ≈ 20 KB (question pack + answer + evaluation)
super-steps/turn ≈ 5 (EVALUATE → SUPERVISOR → AGENT → DECORATE → WAIT)
turns = 8
// checkpoints accumulate the whole growing state each step
≈ 3 – 6 MB retained per completed interview, permanently

10,000 interviews → 30 – 60 GB → OOMKilled
Read this as a leak, not a capacity number

The process does not degrade at some session count — it grows monotonically until the kernel kills it, and every in-flight interview on that pod is lost with no recovery path. At current usage this is invisible. At any real traffic it is a multi-hour-MTTR incident.

Ceiling C — the LLM provider, which is the real wall

This is the ceiling that governs Phase 2 and Phase 3, and it is not an infrastructure problem — it is a provider-quota and unit-economics problem.

The finding that should shape Phase 2

Total volume is cheap. Peak concurrency is the wall. Serving a lakh of users costs under two thousand dollars in inference — but doing it inside a 3-hour evening peak requires 50,000 requests per minute against a provider, which no single account will grant. The Phase 2 design problem is therefore call reduction and concurrency shaping, not raw compute. Cutting 5 calls per turn to 2 is worth more than tripling the pod count.

05

Blocking issues

Ranked by what would hurt most on the day we put this in front of real users. The first four are hard blockers for any public deployment, regardless of scale.

#SeverityIssueWhereConsequence
1Critical Unsandboxed remote code execution — /coding/run writes candidate code into a harness and shells out to python/node with no jail, no seccomp, no user isolation, no memory or CPU limit, and no authentication. routers/coding.py:50 Any anonymous caller gets arbitrary code execution as the app user — reads .env, exfiltrates GROQ_API_KEY and serviceAccountKey.json, pivots into the cluster. The 8s timeout does not contain a fork bomb.
2Critical No authorization on session endpoints — /session/{id}/state, /report, /logs, /answer take a session ID and nothing else. routers/session.py Any known ID exposes another candidate's resume, transcript, and scores, and lets a third party inject answers into a live interview. get_current_user exists but is wired only to /auth/google.
3Critical Single-replica lock-in — MemorySaver plus module-level dicts. agents/supervisor/graph.py:377 Horizontal scaling is impossible, not merely difficult. Any restart, deploy, or crash destroys every active interview.
4Critical Unbounded memory growth — no eviction on checkpoints or session dicts. services/session_engine.py:47 Guaranteed OOM. Timing depends only on traffic. See §4 Ceiling B.
5High SSRF in resume ingestion — urlopen on a caller-supplied URL with no scheme or host allowlist. services/session_engine.py:115 Reaches cloud metadata endpoints and internal services from inside the VPC. Especially dangerous on a node with an instance role attached.
6High CORS is allow_origins=["*"] with allow_credentials=True. main.py:11 An invalid combination that browsers reject inconsistently. Signals no origin policy exists.
7High The session lock is not atomic — if session.get("locked") then set, read-modify-write on a plain dict. routers/session.py:24 Two concurrent answers for one session both pass the check and corrupt graph state. Rare today, systematic once retries exist.
8High Zero observability — no structured logs, metrics, traces, or health endpoint. Errors are print() or swallowed. Everywhere No way to detect that LLM quality has silently degraded to heuristic fallback across the whole fleet.
9High No tests, no CI, no container, no manifests. Repo root Nothing can be safely changed, and there is no artifact to deploy. Blocks every later phase.
10Medium Silent Firestore mock — missing credentials fall back to an in-memory store with no warning. firebase_admin_init.py:55 A misconfigured production deploy appears healthy while writing every user record into a dict that vanishes on restart.
11Medium Hardcoded API base URL — 127.0.0.1:8000 in the axios client. src/api/client.js:4 The frontend cannot be deployed anywhere as-is.
12Medium No rate limiting or abuse control on any endpoint. All routers One script drains the Groq quota for every user, and the bill, in minutes.
13Medium No durable record of a completed interview. Reports are computed from RAM and lost on restart. routers/session.py:51 Results, the actual product value, are the least durable thing in the system.
Credit where due

Secrets are correctly gitignored and none are committed. Browser-side speech keeps audio off the server entirely, which removes an enormous class of bandwidth and compliance problems that most competitors carry. The agent layer is cleanly separated — prompts, nodes, and state live apart, and the graph is genuinely stateless logic. The domain design is sound; the runtime foundation is what's missing. That is the good version of this problem to have.

06

What this implies for Phase 2

Not a design — the design comes out of our discussion. These are the constraints any Phase 2 proposal has to satisfy, derived from the sections above.

  1. Externalise graph state before anything else. Every other scaling move is blocked on replacing MemorySaver with a shared checkpointer. This is the keystone task.
  2. Get the LLM chain out of the request path, or shorten it. 5–6 sequential calls per turn is the cost driver, the latency driver, and the provider-quota driver simultaneously. It is the highest-leverage single change in the system.
  3. The coding runner has to move out of the API process. It cannot be secured in place — it needs a different execution substrate entirely.
  4. Authorization must bind sessions to users before any public traffic, and the token the frontend already holds must start being sent.
  5. Ship the pipeline before the features. Container, tests, CI, and manifests are prerequisites for changing anything else safely — not follow-up work.
  6. Instrument first, then load test. We cannot validate Phase 2 against Phase 3 targets without metrics, and we currently have none.

The open questions — sync versus async turn delivery, checkpointer choice, sandbox substrate, how far to cut the agent chain, and what we are willing to trade for cost — are decisions for the team, not conclusions of this document.
